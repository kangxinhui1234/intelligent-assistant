# 智能助手项目架构分析与优化路线

## 一、项目概览

基于 Spring AI + 阿里云百炼（DashScope）构建的 AI Agent 智能助手平台。

### 技术栈

| 层级 | 技术 |
|------|------|
| 语言 | Java 21 |
| 框架 | Spring Boot 3.3.4 |
| AI 框架 | Spring AI 1.0.0 + Spring AI Alibaba 1.0.0.3 |
| 大模型 | 阿里云百炼 DashScope (主)、火山引擎方舟 (辅) |
| ORM | MyBatis-Plus 3.5.7 |
| 数据库 | MySQL (业务数据) + PostgreSQL pgvector (向量存储) |
| 向量/检索 | ElasticSearch (稠密+稀疏双路检索) |
| 缓存 | Redis (对话记忆持久化) |
| MCP 协议 | Spring AI MCP Client (WebFlux SSE) |
| RAG评估 | Python Ragas (独立评估服务) |

### 项目结构

```
intelligent-assistant/
├── src/main/java/com/kxh/aiagent/
│   ├── agent/          # Agent核心 (BeasAgent → ReActAgent → ToolCallAgent → KxhManus/InvestManus)
│   ├── rerank/         # RAG混合检索模块 (ES稠密+稀疏 + RRF融合 + Rerank重排序)
│   ├── tools/          # 工具集 (WebSearch, PDF, Markdown, 财务查询等)
│   ├── controller/     # API接口
│   ├── vectorstore/    # 向量存储配置
│   ├── app/            # 应用模块 (LoveApp等)
│   └── ragas/          # Ragas评估集成接口
├── kch_search_image_mcp_server/  # MCP图片搜索子服务
├── kxh_agent_front/              # 前端 (Vue3 + Vite)
└── tmp/                          # 临时文件
```

### Agent 架构

```
BeasAgent (基类：状态机 + 循环执行 + SSE流式输出)
  └── ReActAgent (抽象：think → act 循环)
        └── ToolCallAgent (实现：LLM推理 + 工具调用)
              ├── KxhManus      — 通用超级智能体
              └── InvestManus   — 投资研究智能体
```

### RAG 混合检索架构

```
用户查询
   ├── 稠密检索 (ElasticSearch VectorStore, embedding相似度, top5)
   ├── 稀疏检索 (ElasticSearch BM25全文匹配, pdf_docs索引)
   └── RRF融合 (K=60) → DashScope gte-rerank 重排序 → 构建Prompt → LLM回答
```

## 三、技术层面待完善点

### 1. Agent 架构需要重构（最大差距）

**当前状态**：手写 `BeasAgent → ReActAgent → ToolCallAgent → KxhManus` 继承体系，包括状态机、循环检测、SSE流式输出等。

**新版本提供**：`spring-ai-alibaba-agent-framework` 内置完整 `ReactAgent`，运行在 Graph Runtime 之上，自带：
- 自动上下文工程
- 结构化输出 (outputType / outputSchema)
- 对话记忆 (MemorySaver / 持久化 CheckPointer)
- Hook 机制（人工介入、模型调用限制等）
- 最大迭代次数控制 (ModelCallLimitHook)
- 流式传输支持

**建议**：将自研 Agent 框架迁移到官方 ReactAgent，减少维护成本，获得持续更新。

### 2. 缺少多智能体编排能力

**当前状态**：只有单 Agent（KxhManus、InvestManus），没有多 Agent 协作。

**新版本提供**：
- **SequentialAgent** — 顺序执行，前一个Agent输出作为后一个输入
- **ParallelAgent** — 并行执行，结果合并
- **LlmRoutingAgent** — LLM智能路由到合适的子Agent
- **LoopAgent** — 循环执行
- **SupervisorAgent** — 监督者模式
- **Handoffs** — Agent间控制权交接

**建议**：投资研究场景天然适合多Agent：数据采集Agent → 分析Agent → 报告生成Agent。

### 3. 缺少 Graph 工作流引擎

**当前状态**：LoveApp 中有简单的 Graph 工作流 demo（客服分类），但不是基于官方 Graph Core。

**新版本提供**：完整的 Graph Runtime：
- 条件路由、嵌套图、并行分支
- 状态管理 (OverAllState + KeyStrategy)
- 检查点持久化 (Redis/内存)
- 中断与恢复
- 导出 PlantUML / Mermaid 图
- 子图嵌套

### 4. 缺少人工介入 (Human-in-the-Loop)

**当前状态**：Agent 完全自主执行，无人工审批环节。

**新版本提供**：`HumanInTheLoopHook`：
- 对特定工具调用暂停等待人工审批
- 三种决策：approve / edit / reject
- 检查点保存状态，支持异步恢复

**企业场景必需**：投资决策、文件操作、数据库操作等高风险动作需要人工确认。

### 5. 上下文工程不完善

**当前状态**：简单的 system prompt + 工具描述。

**新版本强调**：上下文工程是 Agent 质量的核心：
- 每个Agent精确控制可见信息
- `includeContents` / `returnReasoningContents` 控制上下文传递
- `instruction` 占位符机制 (`{input}`, `{outputKey}`)
- 子Agent间数据隔离

### 6. A2A (Agent-to-Agent) 分布式协作缺失

**新版本提供**：通过 Nacos 集成支持跨服务的分布式 Agent 协调，适合微服务架构下多个 Agent 服务协同。

## 四、企业实际智能体场景待完善点

### 1. 投资研究 Agent — 需要多 Agent + 工作流

当前 InvestManus 是单 Agent 做所有事。企业级应该是：

```
用户提问
  ├── [数据采集Agent] 并行调用财务/估值/行情工具
  ├── [分析Agent] 基于采集数据做深度分析
  ├── [风险评估Agent] 评估投资风险
  └── [报告生成Agent] 生成结构化投资报告 (Markdown/PDF)
```

### 2. RAG 检索 — 需要增量更新与权限控制

当前具备：
- ES 双路检索 + RRF 融合 + Rerank 重排序（Java 实现）
- Python Ragas 评估服务（独立部署）

待完善：
- 知识库增量更新机制（目前只有全量导入）
- 文档权限控制（多租户/多部门隔离）
- 知识库版本管理
- 评估结果反馈闭环（评估结果驱动检索参数调优）

### 3. 缺少对话记忆的结构化管理

当前 Redis 记忆是简单的消息序列化。企业场景需要：
- 长期记忆 vs 短期记忆分离
- 记忆摘要压缩（防止 token 爆炸）
- 用户画像记忆
- 官方 MemorySaver + 持久化 CheckPointer

### 4. 缺少权限与安全控制

- 工具调用无权限校验
- `SystemCmdExec` 工具存在安全风险（可执行任意系统命令）
- 无审计日志
- 无 API 限流

### 5. 缺少可观测性

- 无 Agent 执行链路追踪
- 无工具调用耗时监控
- 无 LLM token 消耗统计
- Spring AI Alibaba 支持 ARMS 可观测性集成

### 6. 缺少错误恢复机制

当前 Agent 遇到错误直接失败。企业场景需要：
- 工具调用重试
- 降级策略（主模型不可用时切换备用模型）
- 检查点恢复（中断后从断点继续）

## 五、推荐研发路线

### Phase 1 — 升级基础设施

1. 升级 Spring AI Alibaba 到 1.1.2.x
2. 引入 `spring-ai-alibaba-agent-framework` 依赖
3. 将自研 Agent 迁移到官方 ReactAgent
4. 配置 MemorySaver + 持久化 CheckPointer

### Phase 2 — 多 Agent 投资研究系统

1. 拆分 InvestManus 为多个专业 Agent（数据采集/分析/风险评估/报告生成）
2. 使用 SequentialAgent + ParallelAgent 编排
3. 加入 HumanInTheLoopHook（投资决策审批）
4. 使用 LlmRoutingAgent 实现智能路由

### Phase 3 — RAG 增强

1. 完善知识库增量更新（ES + VectorStore 同步）
2. 打通 Python Ragas 评估反馈闭环
3. 多租户知识隔离
4. 检索参数自动调优

### Phase 4 — 企业级能力

1. A2A 分布式 Agent（Nacos 注册发现）
2. 可观测性 (ARMS / Prometheus)
3. 安全审计 + 权限控制
4. 错误恢复 + 降级策略

## 六、Spring AI Alibaba 1.1.2 关键 API 参考

### ReactAgent 创建

```java
// 依赖
// com.alibaba.cloud.ai:spring-ai-alibaba-agent-framework:1.1.2.0
// com.alibaba.cloud.ai:spring-ai-alibaba-starter-dashscope:1.1.2.1

ReactAgent agent = ReactAgent.builder()
    .name("agent_name")
    .model(chatModel)
    .instruction("系统提示词，支持{占位符}")
    .tools(tool1, tool2)
    .outputKey("output_key")
    .outputType(ResponseFormat.class)  // 结构化输出
    .saver(new MemorySaver())          // 对话记忆
    .hooks(humanInTheLoopHook)         // Hook扩展
    .build();

// 调用
RunnableConfig config = RunnableConfig.builder().threadId(threadId).build();
AssistantMessage response = agent.call("用户输入", config);
```

### 多 Agent 编排

```java
// 顺序执行
SequentialAgent seqAgent = SequentialAgent.builder()
    .name("seq_agent")
    .subAgents(List.of(agent1, agent2, agent3))
    .build();

// 并行执行
ParallelAgent parallelAgent = ParallelAgent.builder()
    .name("parallel_agent")
    .subAgents(List.of(agent1, agent2))
    .mergeOutputKey("merged_results")
    .mergeStrategy(new ParallelAgent.DefaultMergeStrategy())
    .build();

// LLM 路由
LlmRoutingAgent routingAgent = LlmRoutingAgent.builder()
    .name("routing_agent")
    .model(chatModel)
    .subAgents(List.of(expertAgent1, expertAgent2))
    .build();
```

### 人工介入 Hook

```java
HumanInTheLoopHook hook = HumanInTheLoopHook.builder()
    .approvalOn("dangerous_tool", ToolConfig.builder()
        .description("该操作需要人工审批")
        .build())
    .build();
```

### 最大迭代次数控制

```java
ModelCallLimitHook hook = ModelCallLimitHook.builder()
    .runLimit(5)
    .exitBehavior(ModelCallLimitHook.ExitBehavior.ERROR)
    .build();
```

## 七、向量数据库可切换方案（ES → Milvus → 其他）

### 当前问题

项目中 VectorStore 使用方式耦合度中等：
- 好的地方：所有业务代码都通过 `VectorStore` 接口注入（Spring AI 抽象层），不依赖具体实现
- 需改进的地方：Bean 名称绑定（`@Resource VectorStore elasticSearchVectorStore`），配置类直接写死

### Spring AI 支持的向量数据库

| 向量库 | starter 依赖 | 特点 |
|--------|-------------|------|
| ElasticSearch | `spring-ai-starter-vector-store-elasticsearch` | 当前使用，兼顾全文+向量 |
| **Milvus** | `spring-ai-starter-vector-store-milvus` | 专业向量库，性能强，支持十亿级 |
| PgVector | `spring-ai-starter-vector-store-pgvector` | 已集成，适合中小规模 |
| Redis | `spring-ai-starter-vector-store-redis` | 低延迟，适合缓存层 |
| Chroma | `spring-ai-starter-vector-store-chroma` | 轻量级，适合开发测试 |
| Qdrant | `spring-ai-starter-vector-store-qdrant` | 高性能，Rust 实现 |
| Weaviate | `spring-ai-starter-vector-store-weaviate` | 多模态支持 |

### 可切换设计方案

#### 方案核心：Profile + 策略模式

```yaml
# application.yml
vectorstore:
  provider: milvus  # 可选：elasticsearch / milvus / pgvector / redis

# Milvus 配置
spring:
  ai:
    vectorstore:
      milvus:
        client:
          host: localhost
          port: 19530
        database-name: default
        collection-name: pdf_docs
        embedding-dimension: 1536
        index-type: IVF_FLAT
        metric-type: COSINE
```

#### 配置类设计

```java
@Configuration
public class VectorStoreConfig {

    /**
     * 统一 Bean 名称为 vectorStore，业务层统一注入这个名字
     * 通过 Profile 切换具体实现
     */

    @Bean("vectorStore")
    @Profile("elasticsearch")
    public VectorStore elasticsearchVectorStore(RestClient restClient, EmbeddingModel embeddingModel) {
        return ElasticsearchVectorStore.builder(restClient, embeddingModel)
                .options(new ElasticsearchVectorStoreOptions())
                .initializeSchema(true)
                .build();
    }

    @Bean("vectorStore")
    @Profile("milvus")
    public VectorStore milvusVectorStore(MilvusServiceClient milvusClient, EmbeddingModel embeddingModel) {
        return MilvusVectorStore.builder(milvusClient, embeddingModel)
                .collectionName("pdf_docs")
                .embeddingDimension(1536)
                .indexType(IndexType.IVF_FLAT)
                .metricType(MetricType.COSINE)
                .initializeSchema(true)
                .build();
    }

    @Bean("vectorStore")
    @Profile("pgvector")
    public VectorStore pgVectorStore(JdbcTemplate jdbcTemplate, EmbeddingModel embeddingModel) {
        return PgVectorStore.builder(jdbcTemplate, embeddingModel)
                .dimensions(1536)
                .distanceType(COSINE_DISTANCE)
                .indexType(HNSW)
                .initializeSchema(true)
                .build();
    }
}
```

#### 业务层统一注入

```java
// 所有业务代码统一用 @Qualifier("vectorStore") 注入
@Component
public class KnowledgeImporter {

    @Resource
    @Qualifier("vectorStore")
    private VectorStore vectorStore;  // 不再绑定具体实现名称

    public void importDocuments(List<Document> documents) {
        for (int i = 0; i < documents.size(); i += 10) {
            List<Document> chunk = documents.subList(i, Math.min(i + 10, documents.size()));
            vectorStore.add(chunk);
        }
    }
}
```

#### Milvus 依赖

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-milvus</artifactId>
</dependency>
```

### 改造步骤

1. **统一 Bean 名称**：所有 VectorStore Bean 统一命名为 `vectorStore`，通过 `@Profile` 切换
2. **业务层解耦**：将所有 `@Resource VectorStore elasticSearchVectorStore` 改为 `@Qualifier("vectorStore")`
3. **添加 Milvus 依赖**和配置类
4. **稀疏检索适配**：Milvus 2.4+ 原生支持稀疏向量（Sparse Vector），可替代 ES BM25
5. **混合检索适配**：Milvus 支持 Hybrid Search（稠密+稀疏），可简化 `MultiRetrievalRerankAdvisor`

### Milvus vs ElasticSearch 对比

| 维度 | ElasticSearch | Milvus |
|------|--------------|--------|
| 向量检索性能 | 中等（非专业向量库） | 极强（专为向量设计） |
| 十亿级数据 | 需要大量资源 | 原生支持，分布式扩展 |
| 稀疏向量 | BM25 + 向量分开存储 | 2.4+ 原生 Sparse Vector |
| 混合检索 | 需要自己 RRF 融合 | 原生 Hybrid Search API |
| 全文检索 | 强（核心能力） | 2.4+ 支持但不是强项 |
| 运维复杂度 | 中等 | 较高（需 etcd + MinIO） |
| 适合场景 | 全文+向量混合 | 纯向量/大规模语义检索 |

### 建议

- **保留 ES 做稀疏检索 (BM25)**，Milvus 做稠密向量检索
- 或者直接用 **Milvus 2.4 Hybrid Search** 替代当前 ES 双路 + RRF 方案（更简洁）
- 通过 Profile 让两种方案可以灵活切换，方便 A/B 测试对比检索效果
